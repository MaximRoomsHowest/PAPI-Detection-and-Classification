# Phase 2 — Annotation Schema (2-class → 3-class)

## Taxonomy

| class_id | Original (`papi_lamp_sequences`) | New (`transition-classification-data`) |
|---:|---|---|
| 0 | `papi_light_red` | `papi_light_red` *(unchanged)* |
| 1 | `papi_light_white` | `papi_light_white` *(unchanged)* |
| 2 | — | `papi_light_transition` *(new)* |

The mapping is **purely additive**: class IDs 0 and 1 keep their exact meaning, geometry, and
boxes. Class 2 is introduced for lamps that are geometrically within their angular blend zone
(`|elevation − set_angle| ≤ transition_half_width_deg`, default 0.10°). No existing label is
discarded or remapped — a red/white box only becomes `transition` when geometry (and, in Phase 5,
a human) says the lamp is mid-switch.

## Mapping rules (applied in Phase 3)

For each detection in a frame's `tracks.csv`:

1. Resolve the detection's `physical_lamp_id` (1..4) — already present in `tracks.csv`.
2. Compute that lamp's geometric state via `lamp_state.compute_lamp_state(metadata_row,
   papi_config)` using the **override config** (`configs/papi_edny_transition.yaml`) and the row's
   `nearer_runway`.
3. If the geometric state is `transition` → write class **2**; else keep the original class
   (`0` red / `1` white). Detections without a `physical_lamp_id` (the rare `extra_N` >4-detection
   rows) keep their original class — geometry can't bind them to a lamp.

This is a label *promotion*, not a reclassification of colour: a box keeps its bbox and only its
class id may change from {0,1} → 2.

## Global-state metadata is preserved, not discarded

The five global PAPI states (4W/3W1R/2W2R/1W3R/4R) + TRANSITION are **derivable** from the per-lamp
sequence and are not lost: they remain computable from the per-lamp labels via
`packages/papi/src/papi/global_state.py`, and the per-video `transitions.csv` (red↔white events)
is copied verbatim into the twin. Phase 3 additionally emits `transition_candidates.csv` carrying
the richer per-candidate context (angle, margin, prev/next state, scores).

## Set-angle source (why a separate config)

`configs/papi_edny.yaml` (live) has `set_angle_deg: null` everywhere → FAA defaults, which are not
where these lamps actually transition. `configs/papi_edny_transition.yaml` fills the **commissioned,
±0.02°-validated rwy-24 set-angles** `[2.32, 2.55, 3.12, 3.60]` (innermost→outermost) so the blend
zone is centered on the true transition. rwy-06 stays FAA-fallback (commissioned angles pending) and
is flagged higher-uncertainty. **The live config is never mutated** — promoting commissioned angles
into production is a separate, explicit decision.

## Compatibility with training / export

- **Training:** Ultralytics reads `names` from `data.yaml`; the 3-class `data.yaml` is generated by
  the Phase 3 dataset builder. Class 2 boxes train like any other class.
- **CVAT:** `cvat_export.build_ultralytics(class_names={0:…,1:…,2:papi_light_transition})` already
  accepts the class map — the verification bundle exports/imports the 3-class taxonomy unchanged.
- **Inference (Phase 9, Track A):** add `2: "transition"` to `DETECTION_CLASS_TO_STATE`; the
  existing `LampState` literal already includes `"transition"`, so schemas/frontend need no change
  to *represent* it.
